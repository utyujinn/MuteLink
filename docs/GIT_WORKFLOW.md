# Git運用ルール

## ブランチ戦略

- ソロ開発のため、`main` に直接コミットする(uniahubのようなフィーチャーブランチ運用は
  このプロジェクトの規模には合わないため採用していない)。
- `main` は常にビルドが通る状態を保つ。壊れた状態のコミットを残さない。

## コミット規約

```text
<type>: <概要(現在形・命令形、日本語)>

<必要なら本文で「なぜ」を説明>
```

`type` はこのリポジトリの実際の履歴(`git log`)で使われているもの:
- `feat`: 新機能・新規実装
- `fix`: バグ修正
- `bump`: バージョン番号の更新
- `docs`: ドキュメントのみの変更
- `chore`: 依存更新・設定変更等

例(実際のコミットより):
```text
feat: ローカル音声認識(SenseVoice/Whisper)を選択式モデルとして追加

sherpa-onnx経由でSenseVoice/Whisperをローカル音声認識エンジンとして追加。
モデルはインストーラーに同梱せず、VOICEVOXのキャラクター音声と同様に
Settingsから必要に応じてダウンロードする方式。
```

## コミットのタイミング

- **`git commit`/`git push` はユーザーから明示的に依頼された時のみ行う。** 無断でコミットしない。
  これはこのプロジェクトで繰り返し確認されているルール。
- 依頼された場合、1つの機能追加/不具合修正 ≒ 1コミットを目安にする。TASK.mdの1項目が複数の
  独立したコミットに分かれても構わない(例: バージョン更新とタグ付けは別コミット)。
- コミット前に `git status` / `git diff` で、意図しないファイル(デバッグ用の一時出力、
  ダウンロードしたモデルファイルなど)が混ざっていないか確認する。このセッションでも
  `stderr.txt`/`stdout.txt` のような診断用の残骸を誤ってステージしかけたことがある。

## 破壊的操作について

`git push --force`、`git reset --hard`、ブランチ削除などは、実行前に必ず何が失われるかを
確認し、ユーザーの明示的な許可を得てから行う。フック(`--no-verify`等)のスキップも同様。

## リリース

- バージョンは `tauri-src/src-tauri/tauri.conf.json` の `version` で管理する。
- タグ(`vX.Y.Z`)をpushすると `.github/workflows/release.yml` が起動し、ビルド・
  GitHub Releasesへの公開・更新マニフェストの生成までを自動で行う(未署名ビルド)。
- GitHub Actions側の設定(Environment名・Secretsのパーミッション等)を変更する場合は、
  このリポジトリで過去に踏んだ問題(Environment名の不一致、"Read and write permissions"の
  設定漏れ)を踏まえて確認する。
